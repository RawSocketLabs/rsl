# Migration from v0.1 to the Modular Catalog

## Status and scope

The source migration is complete. Existing consumer repositories are not
silently rewritten: `rsl-rust-core` and `rsl-rust-review` remain thin
compatibility routers, while new installations select the 14 canonical
`rust-*` packages by default.

This migration changed skill discovery and rule ownership. It did not change
explicit repository decisions, organization preferences, or the precedence of
closer local instructions.

## Content map

| Original | Retained | Changed | Behavior change and reason |
|---|---|---|---|
| `skills/rsl-rust-core/SKILL.md` | Stable identity for existing installs and a route to the portable foundation | Domain references moved to their canonical owners; the package is now a short compatibility router | New installs activate `rust-core` and capability owners directly, avoiding one oversized skill |
| `skills/rsl-rust-core/references/*` | Every stable rule ID, directive intent, rationale, exceptions, and source links | Files and individual rules moved according to the ownership map | Selective activation loads only the relevant API, testing, protocol, performance, unsafe, dependency, DSP, async, implementation, or maintenance guidance |
| `skills/rsl-rust-review/SKILL.md` | Review-only scope, evidence gate, severity, and actionable finding shape | Portable procedure moved to `rust-review`; detailed domain checks became routing questions | Review owns finding quality while changed domains own technical rules, preventing duplicated or drifting checklists |
| `skills/rsl-rust-review/references/*` | Risk ordering and consequence-first review | Risk checks now activate canonical domain skills instead of restating their rules | A review may load multiple domain skills based on the diff but reports one coherent findings list |
| `catalog/planned/*.toml` | Approved skill identities, summaries, relations, and intended scopes | Manifests moved beside implemented packages and changed to `status = "implemented"` | All catalog entries are now runtime-installable |
| `catalog/skills.toml` | Stable index contract | Index now points only to canonical package manifests | Compatibility routers are intentionally outside the portable catalog |
| `docs/preference-record.md` | Confirmed decisions, rationale, exceptions, and provenance | Added final protocol unknown-value, corpus, and codec-adoption decisions | Rules distinguish universal guidance from RSL preferences and repository choices |
| `organizations/rsl` | RSL-only ownership and vocabulary preferences | Added indexed libsdr vocabulary, rate, discontinuity, metadata, naming, and observability decisions | Portable skills do not force RSL vocabulary on unrelated repositories |
| `profiles` and `packs` | Existing default profiles as compatibility concepts | Added one-base-plus-capabilities, presets, component overlays, and reusable packs | Mixed repositories can combine protocol, DSP, async, embedded, FFI, performance, security, and workspace defaults without pretending they are identical |
| `references` and `docs/source-ledger.md` | Existing attribution and licensing notes | Added validated trust-tier manifests with revisions, limits, review dates, and refresh rules | External guidance is searchable and auditable but never overrides explicit local policy |
| `examples` | The original ownership lessons | Expanded to nine schema-checked before/review/after/tests transformations | Examples now encode applicability and exceptions rather than slogans |
| `evals` | Clean prompts, isolated fixtures, and private graders | Expanded from 8 to 20 cases and schema 2 metadata | Cases measure skill selection, commands, hard gates, hidden-test interfaces, forbidden regressions, review precision/recall, and unsupported claims |
| `crates/xtask` | Standard-library-only validation, deterministic generation, and guarded installation | Generates all canonical packages, defaults installation to canonical identities, and accepts `--skills` | New installs avoid legacy duplicates while migration installs can explicitly request compatibility routers |
| v0.1 adoption template | Existing consumers remain readable by `inspect-adoption` | New onboarding uses an inspector, approval document, renderer, provenance, and repository validator | No repository policy is finalized or written before inspection, interview, proposal, and approval |
| generated adapters | Deterministic common and Claude layouts plus hashes | Regenerated from all canonical and compatibility packages | Generated views are never hand-edited and drift fails validation |

The stable-rule assignment is recorded in
[`core-review-rule-ownership.md`](core-review-rule-ownership.md). No stable rule
ID was discarded or recycled.

## Compatibility behavior

- A default `cargo xtask install` installs only the canonical packages.
- `--skills` may explicitly select a smaller canonical set or a legacy router.
- Legacy routers do not own duplicated rules and point to their portable
  replacements.
- Existing schema-1 `rsl-rust-standards.toml` files remain inspectable.
- Existing repository-local rules remain higher precedence than profile,
  organization, skill, or external guidance.
- `--replace` remains explicit. Migration must preview targets and preserve
  mature local instructions.

## Consumer migration

1. Inspect the repository, current instruction discovery, installed skills,
   Cargo configuration, CI, tests, unsafe usage, dependencies, and domain
   vocabulary.
2. Identify the installed source revision or classify it as an unprovenanced
   snapshot.
3. Run the onboarding interview and confirm a base, capabilities, components,
   validation, enabled skills, and local overrides.
4. Render repository-specific files in preview mode.
5. Preserve existing local rules as canonical; index rather than duplicate
   them.
6. Install canonical adapters in a staging or otherwise reviewable location.
7. Run discovery smoke tests, repository validation, and relevant evals.
8. Remove legacy routers only after the user approves the migration diff.
9. Record release or commit, content hashes, adapter, profile combination,
   selected skills, migration state, unresolved decisions, and date.

libsdr remains an active pilot whose mature `.agents/rules/` vocabulary is
canonical. bitsandbytes remains a suitable controlled onboarding pilot. Neither
repository is modified merely because this source migration is complete.

   and migration contracts.
2. Created portable core/review packages and compatibility routers.
3. Split every stable rule into one canonical owner.
4. Added onboarding inspection, interview, approval rendering, provenance, and
   repository validation.
5. Implemented testing, protocol, performance, unsafe/FFI, DSP,
   async/concurrency, dependency/security, API, embedded, implementation, and
   maintenance skills.
6. Expanded examples, evaluations, installation selection, and documentation.

These are logical patches in the working change set. Future commits should keep
structural moves, rule expansion, generated output, and unrelated cleanup
separate where repository history permits.
