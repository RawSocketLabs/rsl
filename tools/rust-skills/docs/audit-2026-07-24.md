# Rust Skills Repository Audit — 2026-07-24

## Scope

This audit covered the Rust skills repository, its parent RSL instructions,
runtime skills and references, preference and research records, templates,
generated adapters, `xtask`, eval metadata, fixtures, CI integration, and the
repository instructions of relevant RSL Rust crates. It also used bitsandbytes
and libsdr as read-only adoption pressure tests.

## Current inventory

- Fourteen canonical portable packages plus two thin compatibility routers.
- Machine-readable skill ownership, routing, profile, pack, organization,
  reference, example, migration, and evaluation contracts.
- Stable rule owners for universal judgment, implementation, review,
  onboarding, APIs/errors/docs, testing/property/fuzzing, protocols, DSP,
  performance, async/concurrency, unsafe/FFI, dependencies/security, embedded,
  and maintenance.
- A preference record exceeding 200 decisions, a research report, a human
  source ledger, trust-tiered reference manifests, adoption and authoring
  guides, and migration records.
- A standard-library-only `xtask` that validates sources, generates adapters,
  inspects legacy adoption, selectively installs common or Claude packages, and
  rejects generated drift.
- A standard-library Python onboarding inspector, approval-gated renderer, and
  repository validation dispatcher with human and JSON results.
- Ten curated before/review/after/tests transformations.
- Twenty-two eval fixtures covering activation, precedence, ownership judgment,
  protocol conformance, streaming, review, unsafe, async cancellation,
  dependency features, benchmark validity, onboarding, embedded targets, DSP
  discontinuities, and non-dogmatic readability.
- Root and nested instruction templates plus concise repository-specific output
  contracts.

## Strong foundations

1. Decisions have stable identities, rationale, exceptions, enforcement
   ownership, and sources.
2. Runtime guidance separates mechanical policy from engineering judgment.
3. Review guidance emphasizes consequential and evidenced findings.
4. Canonical sources and generated adapters have a drift gate.
5. Research and licensing provenance are recorded.
6. Eval prompts are kept separate from graders and expected behavior.
7. Adoption is explicit rather than activated merely by repository presence.

## Original gaps and disposition

1. Oversized core/review ownership: resolved through 14 canonical owners and
   compatibility routers.
2. Missing onboarding interview and approval gate: resolved in
   `rust-repository-onboarding`.
3. Rigid profiles: resolved with one base plus composable capabilities, presets,
   and component overlays.
4. Unstructured cross-skill relations: resolved with validated `requires`,
   `routes_to`, and `related` graphs.
5. Missing trust and refresh metadata: resolved with indexed reference
   manifests; the source ledger remains the human explanation.
6. Missing curated transformations: resolved with the initial ten-example
   corpus.
7. No adopted-repository dispatcher: resolved with the generated Python
   validator.
8. Weak eval metadata: partially resolved with schema 2, hidden-case interfaces,
   and external result references; an automated comparative execution service is
   still future infrastructure.
9. Missing consumer provenance: resolved in the generated adoption contract;
   legacy installs remain unprovenanced until explicitly onboarded.
10. Deferred domain skills: resolved; every approved catalog package is
    implemented.
11. Stale or contradictory local facts: addressed by read-only inspection and
    explicit conflict reporting; only a real onboarding run can resolve a
    particular repository.
12. Duplicate mature local rules: addressed by preserving them as canonical and
    generating indexes and overrides rather than copied rule trees.

## Duplication and ownership result

- Every stable rule has one portable owner; no duplicate stable IDs remain in
  canonical references.
- `rust-review` owns finding admission, evidence, severity, confidence, and
  reporting, then routes technical analysis to changed domain owners.
- Profile and pack manifests own reusable defaults. Prose explains their
  semantics but is not the machine-readable source.
- Repository facts remain outside portable runtime skills. Modular adoption can
  preserve and index an existing rule corpus.

## Adoption pressure tests

- **bitsandbytes:** suitable as the first controlled onboarding pilot because it
  has a bounded public-library and protocol surface, strict safe-Rust policy, and
  existing repository instructions.
- **libsdr:** an active pilot installation. Its installed v0.1 skills are
  byte-for-byte equal to the current canonical packages, but no release,
  revision, or checksum is recorded. Its mature `.agents/rules/` corpus must
  remain canonical and be indexed rather than copied into a parallel layout.
  A formal code review is a separate task.

## Baseline validation

The pre-foundation source passed:

```text
cargo xtask validate
cargo xtask generate --check
cargo test --workspace
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
```

This records the v0.1 baseline, not the final validation result. Final modular
validation is rerun after adapter regeneration and is reported with the
completed change.
