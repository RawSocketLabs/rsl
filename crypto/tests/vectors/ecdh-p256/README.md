# ECDH P-256 vector provenance

## Controlling publications

- **Curve:** NIST SP 800-186, *Recommendations for Discrete Logarithm-based Cryptography:
  Elliptic Curve Domain Parameters*, February 2023, §3.2.1.3 (P-256).
  <https://doi.org/10.6028/NIST.SP.800-186>. Accessed 2026-08-28.
- **Primitive and validation:** NIST SP 800-56A Rev. 3, *Recommendation for Pair-Wise
  Key-Establishment Schemes Using Discrete Logarithm Cryptography*, April 2018, §5.6.1.2.2,
  §5.6.2.3.3, §5.7.1.2. <https://doi.org/10.6028/NIST.SP.800-56Ar3>. Accessed 2026-08-28.
- **Encoding:** SEC 1 v2.0, *Elliptic Curve Cryptography*, Certicom Research, May 2009,
  §2.3.3–§2.3.6. <https://www.secg.org/sec1-v2.pdf>. Accessed 2026-08-28.

## Material used

- **Publication:** RFC 5903, *Elliptic Curve Groups modulo a Prime (ECP Groups) for IKE and

- **Fields:** `i`, `gix`, `giy`, `r`, `grx`, `gry`, and `girx` from §8.1 (group 19). The RFC
  states that the shared secret is `girx`; `giry` is not used.

## Conversion policy

Every hexadecimal field is copied into `tests/ecdh_p256/cavp_*_fixtures.rs` by a mechanical
script and decoded pair-by-pair into its printed big-endian byte order by
`tests/ecdh_p256/support.rs::decode`. Coordinates are assembled into SEC 1 uncompressed form by
prefixing `0x04`. RFC 5903 prints values in space-separated 32-bit groups; the spaces are removed
and the digit order is unchanged.

Four PKV cases print a coordinate with 65 hexadecimal digits, which NIST labels out of range.
Those values cannot be represented in a 32-byte coordinate field, so the harness treats them as
rejected at the wire boundary without attempting to truncate them.

No fixture byte is generated by this implementation. Locally chosen boundary inputs are labeled
standard-derived or regression evidence in their test names and comments.

The `p256` crate 0.14.0 is a development-only differential oracle, not an implementation
dependency or a standards authority.
