# ECDSA P-384 vector provenance

## Controlling publications

- **Signing and verification:** NIST FIPS 186-5, *Digital Signature Standard (DSS)*,
  February 2023, §6.4.1, §6.4.2, Appendix A.2.2. <https://doi.org/10.6028/NIST.FIPS.186-5>.
  Accessed 2026-08-28.
- **Deterministic `k`:** RFC 6979, August 2013, §2.3 and §3.2.
  <https://www.rfc-editor.org/info/rfc6979/>. Accessed 2026-08-28.
- **Curve:** NIST SP 800-186, February 2023, §3.2.1.4 (P-384).
  <https://doi.org/10.6028/NIST.SP.800-186>. Accessed 2026-08-28.
- **Encoding:** SEC 1 v2.0, May 2009, §2.3.3–§2.3.6. <https://www.secg.org/sec1-v2.pdf>.
- **Hash:** NIST FIPS 180-4 SHA-384, already recorded in `tests/vectors/sha384/README.md`.

## Material used

### RFC 6979 A.2.6

- **Publication:** RFC 6979, *Deterministic Usage of the Digital Signature Algorithm (DSA) and
  Elliptic Curve Digital Signature Algorithm (ECDSA)*, August 2013, Informational.
  <https://www.rfc-editor.org/info/rfc6979/>.
- **Fields:** the P-384 private key `x`, public key `Ux`/`Uy`, and the `k`/`r`/`s` triples for
  "With SHA-384, message = "sample"" and "With SHA-384, message = "test"". The `k` values are
  published intermediate values checked by the white-box nonce test; the signatures are
  reproduced exactly by public signing and accepted by public verification.
- **Accessed:** 2026-08-28 from <https://www.rfc-editor.org/rfc/rfc6979.txt>.

### NIST CAVP ECDSA SigGen

- **Archive and checksum:** as for SigVer below.
- **File:** `SigGen.txt`, CAVS 11.2, generated 2011-08-16; the `[P-384,SHA-384]` section,
  15 cases.
- **Fields:** `Msg`, `d`, `Qx`/`Qy`, `k`, `R`, `S`. NIST chose `k` at random, so these
  signatures differ from RFC 6979 output; the white-box test injects the published `k` and
  checks `(R, S)`, and the public test checks `Qx`/`Qy` derivation and verification.

### NIST CAVP ECDSA SigVer

- **Archive:** `186-4ecdsatestvectors.zip` from
  <https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program/digital-signatures>.
- **SHA-384 of archive as downloaded 2026-08-28:**
  `fe47cc92b4cee418236125c9ffbcd9bb01c8c34e74a4ba195d954bcb72824752`.
- **File:** `SigVer.rsp`, CAVS 11.0, generated 2011-03-16; the `[P-384,SHA-384]` section,
  15 cases. NIST's verdicts are `P (0 )` for three cases and `F (1 - Message changed)`,
  `F (2 - R changed)`, `F (3 - S changed)`, or `F (4 - Q changed)` for three cases each.
- **Fields:** `Msg` (raw message bytes), `Qx`/`Qy`, `R`, `S`, `Result`.

The archive's `Readme.txt` describes the files as FIPS 186-3 examples; the verification
algorithm is unchanged in FIPS 186-4 and FIPS 186-5 §6.4.2, which is the cited controlling text.

## Conversion policy

Every hexadecimal field is copied into `tests/ecdsa_p384/cavp_*_fixtures.rs` and
`src/signature/ecdsa_p384/cavp_siggen_fixtures.rs` by a mechanical script and decoded pair-by-pair into its printed big-endian byte order by
`tests/ecdsa_p384/support.rs`. Coordinates are assembled into SEC 1 uncompressed form by
prefixing `0x04`; `r` and `s` are concatenated as `r || s`. RFC 6979 messages are the ASCII
bytes of `sample` and `test` without terminators.

No fixture byte is generated by this implementation. Locally chosen boundary inputs are labeled
standard-derived or regression evidence.

The `p384` crate 0.14.0 is a development-only differential oracle, not an implementation
dependency or a standards authority.
